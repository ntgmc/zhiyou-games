# 知识型小游戏设计参考

本文以「深空通信站」为例，规定知识型小游戏的教学、剧情、交互和难度要求，适用于新增游戏，也适用于已有游戏的优化。文中的信息论关卡用于说明具体做法；其他游戏使用自己的知识模型、操作方式和故事情境。

新增游戏，或修改已有游戏的玩法、教程、专业解释、剧情、文案、界面、结算与关卡前，先完整阅读本文，再按本次任务范围落实相关要求。已有游戏可以逐步改进，保留不受本次改动影响的内容。

新游戏允许先发布完整、可玩的前期教程，后续再补独立考核和综合挑战。完善版本需要有逐步提高的后期难度，最终关以已学过基础知识的玩家独立思考及游玩约 1～2 小时为设计目标。这个目标需要真人试玩验证。

## 1. 知识参与玩家的决策

玩家在深空通信站担任通信员，目标是让船队准确、按时收到指令。码长、错误恢复能力和同步费用会实际改变可发送的方案，玩家需要理解它们才能处理请求。

新游戏先明确玩家要完成什么，再确定哪些知识会改变操作结果。一个核心知识点应能对应到可观察的条件、可执行的操作和可解释的后果。

| 设计问题 | 当前做法 | 新游戏参考 |
| --- | --- | --- |
| 玩家是谁？ | 有具体职责的通信员 | 给玩家一个能自然接触主题问题的角色。 |
| 玩家为何行动？ | 船队、观测站和维修员在等指令 | 给出具体对象、任务和完成后的变化。 |
| 知识在哪里起作用？ | 编码、保护和调度共同决定交付结果 | 让知识改变选择、成本或状态，而非只出现在介绍文字中。 |
| 玩家做哪些操作？ | 选择消息、搭树、编辑码字、配置保护、发送 | 设计符合主题的操作，可以是构造、配置、推演或实验。 |
| 如何知道理解了？ | 在变化的条件下独立交付消息 | 用新的条件检验知识迁移，避免只重复教程操作。 |

核心循环可参考：

**接到任务 → 观察条件 → 形成方案 → 操作或实验 → 执行 → 查看结果与原因 → 修改方案或进入下一关。**

简短问答可以用于确认理解，例如重复码教学中的多数票练习。主线仍需要让玩家运用知识完成任务。

## 2. 用可计算的模型支撑结果

当前游戏实际进行信源编码、补位、保护、比特翻转、恢复和解码。是否交付由计算结果决定，同一任务允许玩家使用不同码本和发送组合。

新游戏先实现能独立验证的规则模型，再围绕模型编写关卡和界面：

- 玩家改变配置后，显示的成本、预览和最终执行应使用同一套规则。
- 任务判定检查目标和约束，允许符合条件的不同方案。
- 模型中的简化假设需要说明，尤其是与真实学科结论不同的部分。
- 展示过程应能追溯到具体输入、操作和状态变化。

深空通信站把单轮比特预算与香农信道容量区分开，也说明了可靠同步帧、固定干扰和按原始消息核对结果的教学假设。后续游戏同样需要写清模型适用范围，防止玩家把游戏规则误当成普遍结论。

当前重试使用相同的消息和干扰，便于比较方案。新游戏可以采用固定实例或固定种子；如果随机性本身属于学习主题，应公开它的作用方式，并提供便于比较实验的记录。

## 3. 引导逐步退出，操作权交给玩家

### 默认进入剧情模式

新玩家默认进入剧情模式，每一步只展示当前需要的操作。先通过角色对话说明眼前的问题，再让玩家完成一个明确行动，看到结果后继续。完整控制台或自由操作界面可以由玩家主动进入；玩家已选择的模式可以保存。

后续知识也通过剧情和实际操作引入。当前任务需要的数据、专业概念、公式、规则、工具，以及涉及多个对象或多个步骤的规划，都在首次用到时出现。后面的章节再逐渐交回自主决策。

例如，初期只需要识别对象并执行一次操作；出现资源限制时，再引入成本和比较方法；要处理多个目标时，再展示选择、排序和整体规划。具体内容随主题变化。教程步骤不能只让玩家照着点完按钮，还要解释这一步为何有用。

独立阶段需要保留规划所需的完整条件。按阶段引入信息时，已经学过的规则和当前任务的重要条件仍应能查到。

### 专业知识和名词从零解释

面向第一次接触该主题的玩家，不能假设用户听说或了解过任何专业名词。首次出现时，用日常语言解释它是什么、与眼前任务有什么关系，再配一个能操作或计算的小例子。

- 先说具体含义，再给正式名称。例如先让玩家看到“某条指令出现了几次”，再说明表中的“频数”就是出现次数；使用“频率”时，明确当前展示的是次数还是占比。
- 新定义不能依赖另一个未解释的名词。基础概念也需要说明，例如第一次显示 `bit` 时解释“一位 0 或 1”，第一次使用百分比时说明它在当前任务中表示什么。
- 使用公式前，说明每个符号、单位和条件，并用当前任务的数据算一次。玩家应知道这个结果会影响哪个选择。
- 缩写、图例、指标和工具名称也要解释。保持同一概念的称呼一致；从通俗说法换成正式名称时，说明两者的对应关系。
- 理解当前操作所需的解释直接出现在引导或控件附近。手册、悬浮说明和可展开详情用于复习或补充，不能成为初学者唯一的解释来源。
- 类比需要说明适用范围，数字、保证条件和例外保持准确。通俗解释不能把“满足某些条件时有效”改成“总是有效”。

第一次引入概念时，先让玩家观察或试一次，再要求独立判断。后续章节可以减少重复解释，但应保留回看入口。

### 从教程走向独立任务

当前游戏的学习过程包括以下阶段：

| 阶段 | 当前关卡 | 作用 | 新游戏参考 |
| --- | --- | --- | --- |
| 基础教学 | 1～5 | 引入基本概念，完成小实验和第一次应用 | 每一步只要求一个明确行动；知识在需要时出现。 |
| 独立考核 | 6～8 | 自行选择方案，组合基础知识 | 停止指定正确工具和操作顺序，允许合理尝试。 |
| 进阶挑战 | 9～12 | 观察补位、窗口和后续成本 | 设计能暴露直觉局限的任务，让玩家调整原有理解。 |
| 返航值班 | 13～18 | 手工设计协议、混合保护、跨轮规划 | 增加决策之间的关联，延长需要考虑的范围。 |
| 综合值班 | 19～24 | 更大的队列与更紧的全程预算 | 稳定规则，要求综合使用前面学过的知识。 |

具体关卡数可以调整。新游戏应保留“学会操作后独立解决问题”的转变，后段留出足够篇幅考查已有知识。

教学阶段可以要求玩家先做实验再继续。例如亲手合并码树节点、翻转一位并观察恢复。独立阶段的执行检查只负责格式、操作权限和硬性约束；是否值得这样做、是否会损害后续任务，需要玩家判断。

当前游戏允许发送格式与预算均合法、但纠错不足或后续无法完成的方案。失败后的复盘说明原因。这种安排给独立挑战保留了实际决策空间。

## 4. 难度来自已有决策之间的关联

基础规则掌握后，继续提升难度可以从以下方面入手：

| 难度来源 | 当前例子 | 可复用的设计方法 |
| --- | --- | --- |
| 多种成本相互影响 | 信源长度缩短，保护后的总长度却可能增加 | 让不同指标需要权衡，避免一个工具始终占优。 |
| 局部最优影响后续 | 当前哈夫曼码让下一轮回执装不下 | 让当前选择改变后续状态或可用方案。 |
| 切换有成本 | 更新码本需要同步费 | 在模型适合时引入设置、交接或切换费用。 |
| 时机影响效率 | 清洁窗口可以省掉保护，但容量有限 | 让同一操作在不同条件下产生不同收益。 |
| 小任务存在组合问题 | 每包分别补位，同轮共用方案 | 让分组和顺序影响总成本。 |
| 局部与全程约束并存 | 每轮都装得下，最后却耗尽总预算 | 同时考查单步可行性与完整计划。 |
| 必须完成关键目标 | 综合关每个请求都要交付 | 避免玩家绕过本关知识考查也能过关。 |

新游戏选择适合自身主题的几种关系即可。增加对象数量时，需要增加值得比较的组合或关联，避免只增加重复操作。

后期关卡应提前提供足够条件，让玩家可以规划。深空通信站公开未来请求的频数、抵达时间、期限和窗口。新游戏若以完整计划为主，也应让影响方案的重要条件可见；若以探索或推断为主，则要提供获取条件的有效手段。

完善版本的后期关卡必须有实际挑战，难度逐步提高，主要考查前面知识的综合应用。最终关以已经完成教程、未查看完整参考方案的玩家独立思考及游玩约 1～2 小时为设计目标，需要进行完整规划、尝试和修正。不同主题可以用不同形式实现这个目标，具体关卡数和操作数量不必相同。

当前信息论终关有 14 轮、30 个必要请求，预算为 570 bit。参考方案已经通过实际执行验证，独立解题 1～2 小时的目标尚未经过真人独立试玩验证。后续游戏也要区分“参考方案可执行”和“目标耗时已验证”，不能凭关卡规模宣称玩家一定需要这么久。

解题时间应主要花在观察条件、比较方案、推演后果和调整计划上。不要用强制等待、冗长动画、重复点击或隐瞒必要条件凑时长。长挑战必须支持中途保存和恢复，并提供便于核对的记录与总览。

新游戏的首个版本可以只完成前期教程，先验证知识解释、对话和操作流程，再逐步添加独立考核与后期综合关卡。说明当前版本已经完成的阶段，不把教程的最后一关标成成熟终局，也不添加空白占位关卡。

## 5. 实验工具帮助理解，自动工具减少重复劳动

当前游戏提供码树工作坊和纠错实验台。玩家能直接操纵模型：合并节点、撤销、翻转比特、运行恢复、比较结果。

新游戏可以为抽象知识提供小型实验空间，允许玩家改变条件，并看到过程和结果。实验规模应便于理解，所用规则与正式任务保持一致。

自动工具的职责也需要明确。当前哈夫曼工具只优化所选消息的信源长度，不替玩家计算跨轮分组、同步和未来窗口。后续游戏可以自动处理重复计算，保留选择目标、判断适用条件和制定整体方案的工作。

界面需要说明工具实际优化什么，避免一个“推荐”按钮让玩家误以为已经解决了完整任务。

## 6. 反馈解释因果，提示由玩家选择

结算默认先展示角色回应或任务产生的变化，再用一句通俗的话说明本次学到的知识。回应应接续本关的请求，让玩家知道自己的操作带来了什么结果。没有接收方或对话角色的任务，可以展示实验现象、作品变化或任务对象的状态。

“远方的回应”是信息论游戏的主题表达。新游戏按自己的情境选择回应；技术复盘也不必沿用比特追踪，可以是计算过程、状态变化、策略比较或其他能解释因果的记录。

知识回顾需对应本次操作中的具体现象，例如“常出现的指令写短一点，可以减少发送长度”。避免只说“你学会了某某理论”；新名词仍需解释。这句回顾说明知识或适用条件，与角色对任务结果的回应各有内容。

详细计算、执行追踪和历史记录按需展开，默认结算不一次展示全部技术数据。失败时先说明发生了什么，以及哪个已讲过的条件没有满足，再给可检查的依据；暂未应用到的知识留到后续任务中引入。

新游戏的反馈可以包括：

- 任务层：目标是否完成，哪些对象受到影响。
- 规则层：哪个条件成立或被违反，代价具体是多少。
- 过程层：执行时发生了哪些变化，哪些操作导致了结果。

失败反馈应给出可检查的原因。对于跨多步的问题，需要保留历史条件和执行记录，便于玩家追查早先的选择。

当前独立任务提供三层提示：思考方向、关键约束、完整参考方案。玩家主动逐层打开；查看提示不扣星，但记录“参考提示”，未用提示的成绩单独保留“独立通过”。

新游戏可以复用这套提示结构。参考答案应经过实际规则执行验证，不能只凭文字计算认定可行。

当前星级区分必要任务完成、全部交付和达到效率目标。后续游戏根据主题选择完成度或效率指标，不必照搬三颗星。尤其要区分“完成任务”“完成得更好”和“独立完成”；它们可以分别记录。

## 7. 剧情围绕任务和角色展开

当前剧情通过来电、求援、接驳和交班引入任务。艾拉让玩家看见通信的实际用途，林岚在基础阶段承担引导，后期把发送决定交给玩家。成功后的回信延续前面的请求。

### 对话如何带入操作

参考信息论游戏，让对话接到具体操作和结果：

| 环节 | 信息论例子 | 新游戏要求 |
| --- | --- | --- |
| 提出请求 | 艾拉失去导航，需要一份航线 | 说明谁遇到了什么问题，玩家要达成什么。 |
| 指出眼前条件 | 林岚说明原有写法要发 32 位，这轮只能发 28 位 | 用可观察的事实说明为何需要改变方案。 |
| 解释一个概念 | 观察常见指令，把它写短一些，再认识码树 | 用通俗解释和小例子连接知识与当前任务。 |
| 引导一个行动 | 选择消息、合并两个节点、观察新长度 | 说清本步做什么，使用与界面一致的控件名称。 |
| 看见操作结果 | 玩家看到成本变化，接收方确认收到航线 | 让反馈对应刚才的行动，并给出一句知识回顾。 |
| 逐步交出决定 | 后期林岚提供条件，发送顺序由玩家选择 | 从解释操作过渡到让玩家自己比较和规划。 |

对话可以分成短段，完成当前操作后再继续。下一步根据玩家实际完成的行动推进；出现不符合规则的输入时，说明原因，保留当前步骤和配置。

请求者负责说明需要，引导者帮助理解眼前条件，旁白补充场景。角色不必照搬艾拉和林岚，也不必设置固定人数；对话要符合各自的身份，避免所有人都用教科书口吻说话。

剧情步骤只检查当前教学目标确实完成，例如亲手做过实验。独立关提供完整条件和角色回应，让玩家选择方案，不能要求照着唯一操作顺序通关。

### 文案编辑

新游戏参考：

- 用短场景说明当前任务，角色的话应符合其身份和处境。
- 角色可以教操作、提供条件或回应结果，独立关避免在开场对话中说出完整解法。
- 保持人物关系和任务后果的连续性，让后续关卡接得上前面的行动。
- 文案使用具体动作、物件和对话，减少空泛的成长宣言与重复总结。
- 学科说明保持准确清楚，剧情承担动机和回应。

新增或改写剧情、对话、任务说明、教程、提示和结算等玩家可见文案时，必须使用 `/humanizer`（humanizer 技能）优化。先确保知识准确、解释完整，再检查句子是否自然、角色声音是否一致，以及是否存在空泛总结、刻意对比或重复强调。润色后复核数字、单位、规则、限定条件和术语，不能为了顺口删掉必要信息。

如果当前环境无法读取 humanizer 技能，按上述文案要求完成编辑，并说明未能运行该技能；不要声称已经使用。通信站、太空题材、角色姓名和暗色界面属于本游戏的主题选择。

## 8. 界面按任务阶段展开信息

新游戏默认从剧情模式进入，教学时只显示当前步骤需要的操作。后续数据、公式、模型工具和多目标或多步规划在首次用到时，通过剧情和实际操作引入。进入后面的章节，再逐渐开放更多选项和自主决策。

当前信息论游戏的完整控制台提供更集中的操作视图。新游戏是否需要额外控制台取决于玩法，默认剧情流程仍需完整可玩。高级界面由玩家主动选择，切换时保留当前任务、配置和引导进度。

### 区分任务、对话、练习与正式方案

参考信息论游戏的信息层次，让玩家看清“任务是什么、谁在说话、现在试什么、正式怎么做”。这些内容承担不同作用，应通过位置、标题、间距、边界或其他视觉线索区分，不能堆在一块连续文字里，也不能只靠颜色区分。

| 内容 | 应让玩家看清什么 | 检修站的例子 |
| --- | --- | --- |
| 任务资料 | 谁提出请求、对象是什么、目标与限制是什么 | 报修单列出设备、报修者和需要解决的问题。 |
| 角色对话 | 谁在说话，这段话如何接到当前行动 | 罗师傅解释眼前的检测结果，随后引导一次操作。 |
| 练习空间 | 现在能试什么，操作后发生了什么，是否影响正式任务 | 练习台提供筛选、抽样和比较，说明练习与正式检测的关系。 |
| 正式方案 | 哪些设置会提交执行，费用或结果预览如何变化 | 检修桌配置检测器，以及标红、未标红时分别怎么处理。 |

这四类内容按任务阶段出现，不要求每页同时摆出四个区域。新游戏可以使用适合题材的名称和表现方式；已经进入正式决策时，角色说明和练习入口应给当前任务让出空间。

需要对照资料做配置时，电脑上把相关资料与方案放在相邻区域，减少来回翻找。检修站在同一张检修单内左右并排显示资料和方案；手机上先列资料，再列对应方案，多份任务按各自的“资料 → 方案”成组排列。新游戏根据操作关系选择并排、上下对照、图上操作或其他结构，不强制沿用左右两栏。窄屏调整后，条件、控件和反馈的对应关系仍需清楚。

提示和手册放在主要任务与操作之后，默认保持紧凑。第一次展开提示应直接显示第一层内容；继续查看下一层由玩家主动选择，避免展开后只出现另一个“查看”按钮。必要条件和理解当前操作所需的解释仍直接显示，不能藏到提示里。

### 每款游戏设计自己的视觉与布局

信息层次是共同要求，具体外观由题材和玩法决定。新游戏需要在设计记录中说明主要操作场景、视觉表达，以及布局如何帮助玩家观察和判断。与已有游戏的区别应体现在任务呈现或操作组织上，只换配色、标题、图标和角色名不算完成新的界面设计。

例如，线路规划可以围绕地图组织任务和路径操作，流程优化可以用工序与队列呈现约束，实验类游戏可以把装置、变量和观察结果放在一起。选用这些形式应有实际操作用途；不为外观新鲜增加无用控件、装饰区域或学习负担。

不要把信息论控制台或检修站的“侧栏报修单、角色对话、纸质卡片”整套布局设为后续游戏的默认模板。可以复用站点导航、原生控件、保存反馈和成熟的交互行为，各游戏的主操作区按自己的任务设计。视觉创新仍需保证文字易读、状态可辨、键盘可用和手机可操作。

可复用的交互原则：

- 当前目标、限制条件和主要操作保持可见。
- 教程每步突出一个主要行动，说明做什么、为什么做以及完成后看哪里。新增控件随着任务需求出现。
- 公式、细节追踪和辅助说明按需展开。
- 独立阶段可查询完整任务条件，界面不提前给出最优方案或替玩家判断后续是否可行。
- 当前可操作对象与未来、已完成对象有清楚的状态区分。
- 多对象任务提供总表或其他便于对照的视图，减少反复翻找。
- 复杂配置展示实际费用或结果预览，显示依据与执行规则一致。
- 使用原生按钮、输入和折叠控件，支持键盘焦点、窄屏与减少动画。
- 快捷键尊重正在聚焦的原生控件，不拦截其操作。

难度来自知识判断，界面应让玩家看清任务条件。图形风格、布局和配色需要贴合主题与操作关系，保持各游戏的辨识度。

## 9. 保存过程，允许重新尝试

当前存档包括解锁进度、最好成绩、独立成绩、当前任务状态、历史记录和引导位置。发送后自动保存，重开当前任务保留已有成绩；旧存档能继续使用。

教程每一步的进展和影响继续操作的配置都要自动保存，刷新或再次进入时回到相应步骤。玩家可以重看本章剧情和教学。重看如果会重置当前尝试，要在入口附近说清楚；已经获得的成绩和解锁进度保留。

新游戏使用独立存档键和明确的版本信息，校验读取内容，处理旧版本。长挑战应保存影响后续结果的完整状态，尤其是历史决策留下的设置。

当前按浏览器和站点保存，没有账号或云同步。界面说明换设备、换网址或清理站点数据会影响进度。新游戏继续采用本地存档时也需要保持这一说明。

重试应方便比较方案，完成基础教学后提供跳过或直接进入挑战的入口。提示、手册和实验工具不应反复打断主线。

当前音乐首次访问静音，由玩家主动开启；工具弹窗和中间轮次保持曲目连续，页面隐藏时暂停。新游戏若使用配乐，可复用这类控制行为，具体曲目和切换时机按主题选择。

## 10. 复用工程组织，保持玩法模型独立

当前站点已经具备游戏目录、多页面构建、严格 TypeScript 检查和静态部署。每款游戏使用独立 HTML 入口，首页不会加载信息论引擎或音乐。

| 部分 | 当前实现 | 后续处理 |
| --- | --- | --- |
| 目录与站点入口 | `src/site/catalog.ts`、`home.ts`、`site.css` | 复用站点目录，在元数据中登记新游戏。 |
| 静态构建和预览 | `scripts/build.js`、`server.js` | 沿用现有流程，验证新页面的相对路径和子目录部署。 |
| 文本转义 | `src/shared/html.ts` | 直接复用现有共享工具。 |
| 规则与状态 | 信息论的 `engine.ts`、`types.ts` | 参考纯规则与状态转换的分工，新游戏定义自己的模型。 |
| 关卡与剧情 | `missions.ts`、`story.ts` | 参考数据与交互协调分开的方式，按实际玩法组织。 |
| 界面与复盘 | `app.ts`、`results.ts`、`game.css` | 参考交互模式，避免整体复制通信专属界面。 |
| 存档与音频 | `storage.ts`、`audio.ts` | 检查主题耦合，出现实际共用需求时再提取公共部分。 |
| 验证 | 规则、剧情、存档、音频、部署测试 | 为新玩法建立自己的参考方案、失败案例和交互检查。 |

新增游戏的 TypeScript、CSS 和 HTML 可以由现有构建发现；新增图片、音乐等运行资源需要检查 `scripts/build.js` 中的资源清单并补充。上线检查中也要覆盖新入口。

当前以原生模块和本地资源运行，不需要账号服务或后端参与游戏判定。新增依赖、网络功能或通用引擎需要有具体需求。依据已有游戏实际重合的代码决定共享范围。

## 11. 验证可解性、误区和实际体验

当前游戏用真实执行流程验证各关参考方案，检查常见误区、期限和预算边界、存档恢复、剧情自主操作及部署。浏览器检查覆盖了终关完整流程、中途刷新、提示和不同屏幕尺寸。

新游戏完成时至少回答：

1. 每关是否有经过实际规则执行验证的通关方案？目标成绩是否可达到？
2. 本关要考查的知识是否影响结果？玩家能否绕过它？
3. 是否存在符合格式、但违反知识适用条件或损害后续目标的尝试？失败是否能解释？
4. 一种固定操作或自动工具是否能直接解决所有后期任务？如果可以，独立决策是否足够？
5. 中途保存和恢复是否保留关键状态？旧成绩是否被正确保留？
6. 任务资料、角色对话、练习和正式方案是否容易区分？条件、操作和反馈在电脑与手机上是否便于对照，键盘操作是否可用？
7. 不看完整答案的玩家，能否理解目标、找到下一步并从失败中调整？
8. 不懂主题的玩家能否从默认剧情模式开始？首次出现的术语、缩写、图例和公式是否都有通俗解释？
9. 对话是否接到实际操作和观察结果？教程是否只展示当前需要的操作，并逐步退出指定步骤？
10. 默认结算是否先展示情境中的回应或变化，再给一句对应本次操作的知识回顾？详细过程能否按需打开？
11. 教程步骤和配置是否自动保存？重看本章的入口及其重置范围是否清楚？
12. 玩家可见文案是否经 humanizer 编辑并复核专业准确性？独立任务的开场是否无意中泄露了解法？
13. 完善版本的后期关卡是否要求综合应用已有知识？终关是否以独立思考及游玩 1～2 小时为目标，并记录实际试玩情况？
14. 界面是否根据自身题材和操作关系设计？与已有游戏的区别是否超过换色、改名，并且有助于观察、判断或操作？

规则测试说明方案可行和判定一致。难度是否渐进、关卡是否有趣、独立解题要多久，需要真人试玩补充证据。记录首次理解规则的困难、卡住的位置、提示使用和通关时间，再调整关卡。

## 12. 新游戏立项与单关模板

设计下一款游戏时，先填写以下内容：

| 项目 | 需要明确的内容 |
| --- | --- |
| 主题与学习目标 | 玩家通关后能够解释、判断或独立完成什么。 |
| 玩家角色与任务 | 为什么会遇到这些问题，任务完成后发生什么。 |
| 核心概念 | 概念之间的先后关系，哪些适合实验，哪些适合综合考查。 |
| 初学者解释 | 各术语、单位、图例和公式首次出现在哪一步，如何用日常语言和小例子说明。 |
| 对话与步骤 | 谁提出请求、谁帮助理解条件，每段对话接到哪个操作和观察结果。 |
| 操作与模型 | 玩家能改变哪些条件，规则如何计算结果，哪些是假设与简化。 |
| 约束与权衡 | 什么限制选择，为什么不同方案各有适用条件。 |
| 学习与难度过程 | 当前版本完成哪个阶段，教学如何退出，完善终关如何达到 1～2 小时的独立解题目标。 |
| 反馈与辅助 | 情境回应、一句知识回顾和详细复盘如何安排，实验、自动工具与提示负责什么。 |
| 界面层次与视觉设计 | 如何区分任务、对话、练习和正式方案；电脑与手机如何对照条件和操作；与已有游戏有哪些服务于玩法的布局或视觉区别。 |
| 持续游玩 | 成绩如何记录，何时保存，如何重试与续玩。 |
| 验证计划 | 可执行参考方案、误区案例、交互检查和真人试玩。 |

单关设计记录可使用这个模板，字段供设计讨论使用，不是必须实现的配置 API：

```text
任务情境：
本关学习目标：
已经学过的知识：
本关新知识（综合关可留空）：
首次出现的名词、符号与通俗解释：
对话如何提出问题并接到本步操作：
默认可见操作与后续逐步开放内容：
公开条件与限制：
玩家可执行的操作：
完成条件与评价方式：
需要比较的关键选择：
常见误判及其可观察后果：
参考方案与实际验证结果：
提示：思考方向 / 关键约束 / 完整方案
成功回应与失败解释：
本次知识回顾（一句）：
按需展开的详细过程：
教程断点保存与重看方式：
humanizer 文案检查：
预计独立解题时间及试玩记录：
```

新游戏可以先完成前期教程关卡，确保从默认剧情进入，玩家不依赖既有知识也能听懂解释、完成操作并看见结果。教程可玩后逐步加入独立任务，稳定规则，再扩展后期综合挑战和最终关。已有游戏的优化同样遵循这些要求，围绕本次任务逐步补齐。
