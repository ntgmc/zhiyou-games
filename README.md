# 知游 · 知识型小游戏

一个通用的知识型小游戏站点。首页展示游戏目录，每款游戏有独立入口、完整情境、逐步引导和独立挑战。目前开放信息论「深空通信站」、博弈论「潮汐港：合约与对手」、概率统计「检修站：证据与选择」和图论「山城补给网」：通过通信调度、港口竞合、设备调查与物资运输，把知识用进实际决策。

[游戏目录](https://ntgmc.github.io/zhiyou-games/) · [深空通信站](https://ntgmc.github.io/zhiyou-games/games/information/) · [查看自动部署](https://github.com/ntgmc/zhiyou-games/actions/workflows/pages.yml)

浏览器代码使用严格模式 TypeScript，编译为原生 JavaScript 模块后部署到 GitHub Pages。没有运行时框架，首页与每款游戏分别加载自己的入口和样式；首页不会加载信息论引擎或音乐。页面是普通静态 HTML，支持直接访问、刷新和项目子目录部署。

首页导航提供 `/status/` 状态页和 `/versions/` 版本信息页。状态页展示当前版本已开放的游戏、章节数与知识主题，不提供实时故障监测。版本页展示 `package.json` 中的站点版本、整站内容版本、各游戏的内容版本和构建时间。

内容版本在构建时根据文件内容生成，同样的内容重复构建会得到相同标识。每款游戏的标识包含该游戏的目录信息、页面、代码和样式，以及共用代码与资源；共用资源更新时，多个游戏的标识可能一起变化。构建时间单独记录，不参与内容版本计算。源码开发模式显示“开发预览”，发布包显示实际版本。版本标识与游戏存档格式版本分别维护。

## 启动

需要 Node.js 20 或以上版本（推荐与 CI 一致的 Node.js 24）和 npm。先安装锁定的开发依赖，再启动：

```powershell
npm ci
npm run dev
```

在浏览器打开 `http://127.0.0.1:5173/` 查看游戏目录，进入 `/games/information/` 游玩信息论游戏。开发命令先编译 TypeScript，再同时运行编译监听和静态服务器；修改后刷新浏览器即可。`npm start` 是同一命令，按 Ctrl+C 会停止两个进程。可以通过 `PORT` 环境变量更改端口。

```powershell
$env:PORT = 8080
npm run dev
```

检查类型与运行规则验证：

```powershell
npm run typecheck
npm test
```

进行浏览器交互测试时，可以打开 `http://127.0.0.1:5173/games/information/?test=1`，使用独立的测试档案。也可以从 `/?test=1` 的目录进入，测试参数会随游戏链接保留。

游戏迁移后继续使用原有的 `deep-space-comms-save-v1` 存档和音乐偏好键。同域名下原先在首页留下的星级、解锁进度和当前值班可以直接恢复。

## 深空通信站

默认从剧情模式开始：玩家接到信使号驾驶员艾拉的来电，由值班长林岚带着完成通信。每章先用简短对话引入问题，再只展示当前步骤需要的操作。

- 第一章依次完成选消息、点击指令观察二进制码字、核对空间和发送。
- 第二章先读频率，再在带动态提示的码树里亲手合并节点。
- 第四章通过多数票小实验理解重复码，再用于避障请求。
- 第五章先制造一位错误并亲眼看见恢复，再选择汉明保护。
- 从第 6 关开始完全交回自主决策：没有指定操作顺序，不要求先点击正确保护才准许发送。
- 新知识在使用时出现，公式和比特追踪按需展开；结算优先展示远方的回应。
- 剧情步骤、练习状态也会保存。值班菜单支持重看本章、选择航段、查阅手册和切换完整控制台。

24 个航段分为 1～5 基础教学、6～8 独立考核、9～12 进阶挑战、13～18 返航值班和 19～24 综合值班。基础知识包含定长编码、前缀码、信息熵、哈夫曼编码、三次重复码与汉明 (7,4) 码；后续任务需要同时处理压缩、纠错、期限、码本同步和全局预算。

### 进阶挑战

| 航段 | 玩家需要作出的判断 |
| --- | --- |
| 9 · 短码的代价 | 最短信源表示是否真的有最低发送成本？比较独立小包的补位与保护。 |
| 10 · 安静的一轮 | 一轮清洁信道应留给谁？依据三轮预报调度，而不只是每轮都开汉明。 |
| 11 · 留给下一条消息 | 当前省两位是否值得？后续消息已经预告，码本更新可能让下一轮无法完成。 |
| 12 · 最后一盏灯 | 在四个不同窗口中安排六个请求，同时处理抵达轮次、期限、保护、码本与总预算。 |

### 返航值班

第 12 关修好馈线后，艾拉带着返航编队再次联系通信站。第 13～18 关都有完整窗口预报和三层可选提示，开场不指定操作顺序。每个请求都必须准确交付，不能放弃难发的包来过关。

| 航段 | 玩家需要作出的判断 |
| --- | --- |
| 13 · 接通返航线 | 很短的回执该用重复码还是汉明码？发长航线时还要考虑下一轮留下的实际码字。 |
| 14 · 两艘船的码本 | 手工安排码长，让一套协议撑过三轮。只优化当前消息会卡住后面的航线。 |
| 15 · 七份小包 | 比较每包补位与同步费，决定何时沿用码字、何时换成变长码或定长码。 |
| 16 · 安静窗口的队列 | 五轮安排八个请求。提前多发一个短包可能耗尽最后的总预算。 |
| 17 · 先送过去的协议 | 未来回执尚未抵达，码本就得先准备好；末段频率变化后也要算更新费用。 |
| 18 · 等最后一艘船 | 六轮交付十个必要请求，手工码本、混合保护和两次协议交接要一起规划。 |

### 综合值班

第 19～24 关综合运用前面学过的规则，逐步扩大队列，收紧全程预算。请求的抵达与期限跨越多个窗口，分组、码本和保护方式需要一起规划。六关均要求交付全部请求，仍提供三层按需展开的提示。

| 航段 | 窗口 / 请求数 | 总预算 / 三星目标 | 规划重点 |
| --- | --- | --- | --- |
| 19 · 把队列排完整 | 6 / 12 | 239 / 227 bit | 给长包安排静区，比较同轮分组与等待的成本。 |
| 20 · 晚到的接驳艇 | 7 / 14 | 262 / 254 bit | 给后续抵达留位置，兼顾短回执需要的实际码字。 |
| 21 · 两边都在等 | 8 / 17 | 354 / 348 bit | 多次协议交接，逐包计算补位，给后段队列腾出容量。 |
| 22 · 整张航道图 | 10 / 23 | 424 / 420 bit | 从早期和末窗双向检查，把局部容量与累计支出一起算清。 |
| 23 · 交班之前 | 12 / 26 | 530 / 528 bit | 只剩 2 bit 预算余量，后段同步需在前一窗口安排。 |
| 24 · 一整班的灯 | 14 / 30 | 570 / 570 bit | 五个清洁窗口与多段干扰交替，综合安排全程分组、混合保护和协议更新。 |

终关以独立规划和尝试约 1～2 小时为设计目标。这个耗时尚未经过真人独立试玩验证，熟练程度、计算方式和提示使用都会影响实际时间。游戏没有等待计时或强制拖延，发送进度会自动保存，可中途离开再继续。

值班菜单提供「进入进阶航段」「接通返航线」和「进入综合值班」，可以直接从第 9、13 或 19 关开始。已完成第 8、12 或 18 关的旧存档会自动解锁下一关，已有星级和发送记录保留。

实战界面默认展示任务条件，提供每包频数、接收端码本、窗口预报、完整费用与历史计划。剧情界面将未来请求收进可展开的预告，当前可发消息优先显示。综合值班还有整班请求总表，集中对照频数、抵达轮次、期限和交付状态，窄屏可横向滚动。不会提前判断方案是否可靠或未来是否可行；发送按钮只检查码本格式、抵达条件和预算。

「生成哈夫曼码」仅优化当前所选消息的信源长度，不计算同步、独立补位或未来窗口。分包费用可展开查看，带同步的任务可精确沿用接收端码本。不同窗口的实际干扰参与比特级模拟，发送费用会计入整次预算。

独立任务的提示分三层：思考方向、关键约束、完整参考方案，需要玩家主动逐层展开。使用提示不扣星，但会标注本次参考提示；未使用提示的通关会单独保留「独立通过」标记与最好星级。

- 手工构造码树：选择两个节点合并，可撤销，并比较自己的平均码长与最优长度。
- 实时码本校验：阻止前缀冲突、重复码字和非法输入。
- 汉明码实验台：点击比特制造单错或多错，观察校验、综合值与误纠正。
- 可复现干扰：重试使用相同的消息和干扰种子，方便比较方案。
- 发送后逐包复盘：显示实际发送、信道翻转、恢复数据和解码指令。
- 本地保存：当前关卡、当前值班、解锁状态与最好星级保存到当前浏览器。
- 响应式布局、键盘焦点与减少动画支持。

页面无运行时框架依赖，采用系统中文与等宽字体。所有游戏模块、图片和音乐都来自当前站点，没有外部字体、第三方音乐或 CDN 请求。

## 原创音乐

页头的「开启音乐」按钮会打开音量与选曲面板。第一次访问保持静音，点击后才创建播放器并下载当前曲目。音量默认为 30%，音乐开关、音量和选曲偏好单独保存在浏览器里。

| 配乐 | 氛围 | 自动使用场景 |
| --- | --- | --- |
| 轨道晨光 | 慢速合成器、空间感与零星铃音 | 各章剧情开场 |
| 码间微光 | 轻柔规律的琶音 | 前三章的实战练习 |
| 风暴边界 | 低频脉冲、克制的紧张感 | 第四章起的实战、失败后的调整 |
| 远方回声 | 温暖和声、舒展的铃音 | 章节成功与回信 |

自动选曲只跟随章节开场、进入实战与任务结果。打开或关闭码树、通信手册、提示、纠错实验等窗口，以及发送动画和中间轮次结算，都保持当前曲目连续播放；切换剧情界面与完整控制台也不会单独触发切歌。也可固定播放任一曲目。切歌约 1.8 秒淡入淡出，关闭音乐短暂淡出；页面隐藏时暂停，返回时恢复。重新打开页面后遵循浏览器播放限制，等下一次交互再恢复。

四首曲目均由项目内合成脚本原创制作，无第三方歌曲或录音采样，音频可随游戏复制、部署和公开播放。详细说明见 `assets/music/README.md`。音频文件已经包含，游玩和构建不需要 Python 或音频创作工具。

## 发布前构建

运行：

```powershell
npm run check
npm run preview
```

`npm run check` 依次完成类型检查、测试和发布构建。也可单独运行 `npm run build`；构建本身会先编译并阻止有类型错误的代码进入发布包。

在 `http://127.0.0.1:4173/` 查看真实发布包。`dist/` 包含目录首页、独立游戏页面、编译后的运行时模块、样式、音乐、图标、分享图片与托管规则；不包含 TypeScript 源码、测试、生成脚本、本地预览服务器和开发依赖。

构建会为运行资源生成内容版本路径，例如 `static/a1b2c3d4e5f6/`。HTML 页面每次重新验证，版本化资源使用长期缓存，修改代码后会得到新路径。构建根据当前源码发现模块和样式，并为首页及各游戏页面重写资源路径。构建仅清理本项目内的普通 `dist/` 文件夹；遇到替代链接时停止。

所有模块与音频地址使用相对路径，既可部署在站点根目录，也可部署在 GitHub Pages 这样的项目子目录。可以本地验证子目录：

```powershell
node server.js --dist --base=/zhiyou-games
```

对应 `http://127.0.0.1:4173/zhiyou-games/`。

确定正式网址后，设置 `SITE_URL` 再构建，以写入 canonical、Open Graph 图片与完整分享网址：

```powershell
$env:SITE_URL = "https://你的正式域名/"
node scripts/build.js
```

若采用项目子目录，填完整网址，例如 `https://用户名.github.io/zhiyou-games/`。未设置时不写入虚构域名，游戏仍可正常运行。分享封面为 `assets/share-card.png`；是否展示卡片由分享平台决定。

## 托管配置

默认采用 GitHub Pages，推送至 `main` 后由 GitHub Actions 自动完成测试、构建与发布。其余配置可用于迁移到其他静态托管平台。

### Cloudflare Workers Static Assets

仓库中的 `wrangler.jsonc` 指定 `dist` 为静态资源目录，无需额外后端代码。实际发布时，在已登录 Cloudflare 的环境构建后执行：

```text
npx wrangler deploy
```

若使用 Workers 的 Git 仓库构建，构建命令填 `npm run build`，部署命令填 `npx wrangler deploy`。可以在构建环境中设置正式 `SITE_URL`。

### Netlify / Cloudflare Pages

Netlify 的 `netlify.toml` 已设置构建命令 `npm run build` 与发布目录 `dist`。也可以将本地构建出的 `dist` 直接作为静态网站发布包。

Cloudflare Pages 可使用同样的构建命令和发布目录。`dist/_headers` 提供缓存与响应头规则。无需将游戏地址重写为 SPA；首页和各游戏都有独立的 `index.html`，游戏内部的关卡通过本地状态切换。

### GitHub Pages

仓库为 `ntgmc/zhiyou-games`，Pages 地址为 `https://ntgmc.github.io/zhiyou-games/`。发布源使用 GitHub Actions，工作流位于 `.github/workflows/pages.yml`。

每次向 `main` 推送会先执行 `npm ci`、严格类型检查和游戏、音乐、部署测试，再构建、上传 `dist` 和发布，并使用 Pages 的正式网址填写分享信息。发布后检查目录首页、信息论游戏页、JS、CSS、分享封面与四首配乐的公开访问和 MIME 类型。任一步失败会使工作流显示失败。

Pull Request 会运行同样的测试与构建，但不发布网站。也保留了 `workflow_dispatch`，可在 Actions 手动运行「CI and deploy zhiyou-games to GitHub Pages」重新发布。

后续更新：

```powershell
git add .
git commit -m "Update game"
git push
```

不需要手动上传 `dist`；它始终由 CI 从源码重新生成。

### 自己的服务器

将 `dist` 的内容复制到网站的静态根目录即可。`server.js` 用于本地预览，不需要在生产服务器上运行。使用 Caddy 时可参考 `deploy/Caddyfile.example`，替换域名与磁盘路径。使用其他服务器时对应设置 HTML 重新验证、`/static/*` 长缓存和 JS / MP3 MIME 类型。

`_headers` 由 Cloudflare / Netlify 解析；GitHub Pages 不会应用这些自定义响应头，自建服务器则需在自身配置中设置。游戏本身不依赖这些头才可运行。

玩家的档案和音乐偏好保存在当前浏览器的当前站点中，不会云同步。换设备、换域名或清理站点数据后，原进度不会自动跟随；游戏菜单也会说明这一点。

## 模拟规则

1. 指令为前进、左转、右转和停止，游戏使用已知的消息频率。
2. 各消息包独立进行信源编码、补位、保护与解码。汉明成本为 `ceil(信源长度 / 4) × 7`。
3. 任务必须在截止轮次结束时准确交付。预算按轮重置，剩余比特不结转。
4. 第 1～7 关假设码本预共享，未计包头开销。
5. 第 8 关修改码本产生 12 bit 的同步成本，使用可靠控制帧；同步成本包含在当轮预算中。这是简化教学成本。
6. 干扰是固定的教学模型：清洁信道、每包单次翻转，或每个连续 7 比特恰有一位翻转。
7. 普通汉明 (7,4) 保证纠正每块一位错误，多位错误可能误纠正；不是扩展 SECDED 码。
8. 发送后与原始消息核对是教学复盘。真实接收端若没有额外检测，不总能知道解码结果是否正确。
9. 本轮容量指发送长度预算，不代表香农信道容量；游戏没有模拟容量定理的渐近条件。
10. 星级：必要任务全完成为 1 星；所有消息交付为 2 星；所有消息交付且总成本达到该关效率目标为 3 星。
11. 带预报的任务每轮使用自己的预算与干扰模型，所有预报从任务开始就公开。指定未来抵达的消息不能提前发送，但频率、抵达轮次和期限可见。
12. 带整次预算的任务，所有轮次的数据、补位、保护和同步费用都计入总量；合法的单轮方案仍可能耗尽后续额度。

## 项目结构

- `index.html`：知游目录首页。
- `games/information/index.html`：信息论游戏独立入口。
- `src/site/catalog.ts`：游戏目录元数据，新增游戏在此登记。
- `src/site/home.ts` / `site.css`：目录卡片与首页样式。
- `status/index.html` / `versions/index.html`：游戏状态与版本信息入口。
- `src/site/info.ts`：状态与版本展示，复用游戏目录；发布信息由构建写入页面。
- `src/shared/html.ts`：HTML 文本转义。
- `src/games/information/types.ts`：任务、码本、状态和剧情的类型。
- `src/games/information/engine.ts`：纯编码算法、干扰与状态机。
- `src/games/information/missions.ts`：关卡、任务和通信手册。
- `src/games/information/story.ts`：章节剧情与引导状态。
- `src/games/information/app.ts`：游戏启动、界面和交互协调。
- `src/games/information/storage.ts`：存档校验、兼容读取和保存。
- `src/games/information/tree.ts` / `lab.ts`：码树与汉明纠错实验。

## 添加另一款知识游戏

新增游戏或优化已有游戏的玩法、教学、剧情、界面与关卡前，必须阅读并遵循 [知识型小游戏设计参考](docs/knowledge-game-design.md)。默认剧情引导、零基础知识解释、文案编辑和后期难度等要求也写在根目录 [AGENTS.md](AGENTS.md) 中。新游戏可以先完成前期教程，后续逐步补齐独立与综合挑战。

1. 在 `games/<游戏标识>/index.html` 添加独立 HTML 入口，资源路径相对于该页面填写。
2. 在 `src/games/<游戏标识>/` 放置自己的 TypeScript、样式、规则、关卡和剧情。无需依赖信息论的任务模型；仅提取实际共用的功能。
3. 在 `src/site/catalog.ts` 登记标题、知识主题、简介、标签、章节数和 `./games/<游戏标识>/` 地址。目录会自动渲染这张卡片，构建会自动包含新页面、模块和样式。
4. 为新游戏添加规则与交互测试，使用独立的存档键，然后运行 `npm run check`。

目前目录包含「深空通信站」「潮汐港：合约与对手」「检修站：证据与选择」和「山城补给网」四款游戏。后续游戏使用自己的知识模型与玩法；没有创建尚未实现的游戏或空白入口。

本站仅使用浏览器本地存储，没有账号、后端数据上传或多人通信功能。

## 潮汐港：合约与对手

访问 `/games/game-theory/`，经营白帆运输，与岑舟的船队共享港口。24 章分为 1～8 入门与迁移、9～12 进阶航线、13～16 综合值班、17～19 新港订单、20～24 独立交班，运用最佳回应、占优策略、纳什均衡、保证金承诺、参与与激励约束、跨轮资金规划、重复博弈和有限终局。可以直接进入任意章，也可从第 9、13、17 或 20 章开始挑战。

玩家制定保证金与合作分账合同，再密封提交错峰或抢先行动。对手依据公开收益与策略独立行动，不读取玩家尚未揭晓的选择。结果由同一个纯规则模型计算，复盘提供净收益表、单方偏离收益与另一种行动的反事实比较。稳定合作任务同时检查双方激励，不能只凭一次碰巧错峰通关。

第 6 章采用恒定延续概率的重复博弈，第 12 章比较三段不同延续概率的独立关系，第 19 章进一步比较不同货价下的双方合作激励，结算整段关系的期望收益；不抽样、不把期望当作已到账现金。其他章节有明确班次数，保证金在当班守约后返还，手续费实际消耗，周转资金只作为签约前的余额约束。第 11 章起的部分任务另有累计担保登记上限，现金退款不会恢复登记额度。

后续挑战要求同时规划双方现金、双向分账和全程担保。第 24 章有 24 班货，收入目标 244，累计担保上限 168、三星目标 166；每班都须稳定合作。固定合同和只优化当前收入或保证金无法完成整天的排班。终关以独立规划及游玩约 1～2 小时为设计目标，这个耗时尚未经过真人独立试玩验证。

游戏提供独立实验台、航运手册、三层可选提示、独立成绩与效率星级。当前行动、草稿、提示状态、结算与成绩自动保存到独立的 `tidal-harbor-save-v1` 存档；`?test=1` 使用隔离测试档案。读取存档时从合法的历史决策重建账目，不信任保存的现金或结果。

规则与关卡说明见 [潮汐港设计与模型](docs/tidal-harbor.md)。`test/game-theory.test.js`、`test/game-theory-story.test.js`、`test/game-theory-challenges.test.js`、`test/game-theory-voyages.test.js` 用真实结算流程验证全部参考方案、资金与合同边界、剧情步骤、累计额度、局部选择造成后续失败及断点恢复；部署测试覆盖入口、样式、模块与项目子目录。

## 检修站：证据与选择

访问 `/games/probability/`，接下街区的设备检修单。8 章首版从零解释占比、随机频率、条件概率、误报、贝叶斯更新和期望损失，随后核查重复报告、取样推断批次状态，最后独立分配调查费用与工时。

玩家选择检测器并预先安排标红、未标红时的处置；批次任务选择样本数和更换条件。成绩按所有结果分支的期望总损失计算，单次实际故障和损失另行展示。同一章重试保留正式设备及检测结果；不同合理策略都能通过公开目标。

默认进入逐步剧情，教程与配置自动保存，可重看本章或主动进入检修桌。提示分三层，独立通过成绩单独保留。正常存档为 `repair-station-save-v1`，`?test=1` 使用隔离档案。读档按合法配置重算执行结果，不信任保存的损失或真实状态。

规则、教学简化与验证记录见 [检修站设计与模型](docs/repair-station.md)。`test/probability.test.js` 验证 8 章参考方案并枚举合法策略，检查重复证据、概率与样本边界、资源约束、随机结果和成绩分离、教程恢复及损坏存档。首版完成前期教学与独立考核；后期统计实验与长篇综合挑战尚未制作，趣味及真人耗时仍需试玩验证。

## 山城补给网

访问 `/games/network/`，为暴雨后的街区安排补给。8 章首版从路线方向和每段运费开始，逐步学习分配通道容量、撤回原计划中的一段安排，再用最小割证明最多能运多少箱，最后独立满足两个接收站的需求。

玩家在地图或通道按钮中选路，填写箱数并编辑运输计划。桌面端把地图与选路并排，下方核对计划和确认发货；手机端依次展示。新增路线与反向改排共用同一套容量规则，预计送达量、运费和执行结果由同一模型计算。容量、库存和预算是执行限制，合法但未达到任务目标的方案也能执行并查看原因。

默认剧情逐步引入知识，支持自由调度和重看章节。提示入口放在当前操作下方，点击直接显示第一条，再由玩家逐层查看；提示成绩与独立成绩分别保留。运输计划、未完成路径、分界选择和引导步骤自动保存到 `mountain-network-save-v1`，`?test=1` 使用隔离存档；读档时重新计算结果。

规则、简化条件与验证范围见 [山城补给网设计与模型](docs/mountain-network.md)。测试执行全部参考方案、枚举整数路线分配与分界，并检查超载、残量调整、接收点缺口、教程和存档。费用优化、修复工程、跨班运输及成熟综合终关尚未制作，真人理解、趣味和耗时需要试玩验证。
